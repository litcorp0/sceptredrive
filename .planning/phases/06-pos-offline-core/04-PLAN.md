# Plan 04 — Offline PIN, Bindings, Shifts, Console PIN Reset

**Goal:** A manager sets a temporary PIN in the console; the cashier authorizes that PIN
online once on a terminal, changes it, and can then log in with the PIN offline after a
restart. Failed attempts lock the binding and a cached manager PIN unlocks it. Shifts open,
take cash in/out, and close with expected-vs-counted variance entirely offline, and the
server applies the same shift events idempotently.

## Task 1 — Staff PIN service, routes, and binding invalidation

**Files:** `api/src/modules/identity/staff.service.ts`,
`api/src/modules/identity/staff.repository.ts`,
`api/src/modules/identity/staff.routes.ts`,
`api/src/modules/identity/staff.controller.ts`,

`api/src/modules/identity/staff.schema.ts`,
`api/src/auth/auth.ts`, generated `api/migrations/0008_*.sql`,
`api/src/modules/identity/staff.test.ts`

- Add `pinMustChange` boolean notNull default false to `user` and to Better Auth
  `additionalFields` with `input: false`, `returned: false`. Migration generated by
  Drizzle; no data backfill needed.
- `POST /api/staff/:id/pin` (`requireSession`, `requirePermission('staff.pin.reset')`,
  branch access via `staff.service`): body `{ pin: string }` 4–6 digits, reject trivial
  sequences (`0000`, `1234`, repeated digits). Hash with the existing `argon2Options`
  (Argon2id 64 MiB/t=3/p=4), set `pinVersion = pinVersion + 1`,
  `pinMustChange = true`, revoke all active `pos_staff_binding` rows for the staff member,
  and audit `staff.pin.reset` (no PIN/hash). Return `{ staffId, pinVersion }`.
- `GET /api/staff/:id/pin-status` (staff.read) returns `{ hasPin, pinVersion, pinMustChange,
  activeBindings }` — never the hash.
- Hook invalidation into `updateStaff` when role/branch/isActive changes and into
  `deactivateStaff`: revoke bindings and bump `pinVersion` (so stale devices fail closed).
  Deactivation keeps the PIN hash but no binding can be created.
- Tests: manager sets a cashier PIN in own branch → 201, hash verifies with argon2,
  `pinVersion` bumped, `pinMustChange` true; manager other branch → 403; cashier → 403;
  invalid/trivial PIN → 400; reset revokes bindings; role change bumps version; response
  never contains `pinHash`.

**Verify:** HTTP tests; SQL shows `user.pin_hash` changed and bindings revoked;
`check-types`.
**Commit:** `feat(api): add staff pin reset and binding invalidation`

## Task 2 — Device staff authorization and PIN change

**Files:** `api/src/modules/pos/pos.schema.ts` (binding table already in Plan 01),
`api/src/modules/pos/pos.service.ts`, `api/src/modules/pos/pos.repository.ts`,
`api/src/modules/pos/pos.types.ts`, `api/src/modules/sync/sync.routes.ts`,
`api/src/modules/sync/sync.controller.ts`,
`api/src/modules/sync/sync.validation.ts`, `api/src/modules/sync/sync.test.ts`

- `POST /api/pos/staff/authorize` (device JWT, rate-limited 10/min/device): body
  `{ staffCode?: string, email?: string, pin: string }`. Resolve the staff by staff code or
  email; require active user, `staffId` present, branch matches the device branch for
  CASHIER, role in `CASHIER|MANAGER|ADMIN` (a manager/admin may authorize on any retail
  terminal in their scope); verify `pinHash` with `verifyPassword`. On failure return a
  generic 401 (`PIN_INVALID`) and audit the failure without the PIN. On success:
  - revoke any existing active binding for `(device, staff)` (one active);
  - create a binding with a 32-byte random token, store its HMAC-SHA256 hash, 90-day
    expiry, current `pinVersion`, role, branch;
  - audit `pos.staff.binding.created`;
  - return `{ bindingId, bindingToken, expiresAt, staff: { userId, staffId, name, role },
    pinVersion, mustChangePin }`. The token is returned once only.
- `POST /api/pos/staff/change-pin` (device JWT + binding token): body
  `{ currentPin, newPin }`; verify current PIN and binding, reject if `mustChangePin` is
  false only when the cashier chooses to change (allowed either way); update `pinHash`,
  `pinVersion++`, `pinMustChange=false`, revoke all bindings for the staff, create a fresh
  binding for this device, return it; audit `staff.pin.changed` (actor = staff).
- `POST /api/pos/staff/binding/validate` (device JWT + binding token): returns
  `{ valid, staff, pinVersion, mustChangePin }`; used by the device on boot when online.
  Never accepts a staff pin.
- A binding is inactive if `revokedAt IS NOT NULL`, expired, staff inactive, pinVersion
  differs, or branch/terminal mismatch. Uploads (Plan 05) call the same validator.
- Tests: authorize with correct/incorrect PIN; generic error; binding token hashed at
  rest; duplicate authorize revokes the old binding; PIN change invalidates old bindings;
  stale `pinVersion` → invalid; manager can authorize at a branch terminal; cashier cannot
  authorize at another branch; rate limit.

**Verify:** HTTP tests; SQL `binding_token_hash <> bindingToken`; audit rows present;
`check-types`.
**Commit:** `feat(api): add device staff bindings and pos pin change`

## Task 4 — Device PIN module, lockout, and manager unlock

**Files:** `desktop/src/renderer/lib/auth/pin.ts`,
`desktop/src/renderer/lib/auth/bindings.ts`,
`desktop/src/renderer/lib/auth/session.tsx`,
`desktop/src/main/ipc/pin.ts`, `desktop/src/preload/preload.ts`,
`desktop/src/renderer/routes/login.tsx`,
`desktop/src/renderer/components/auth/pin-pad.tsx`,
`desktop/src/renderer/components/auth/manager-unlock.tsx`

- Main-process `pin.hash(pin, salt)` and `pin.verify(hash, pin)` using `@node-rs/argon2`
  with `argon2Options`; inputs validated (4–6 digits, base64 salt 16 bytes); no logging.
  Add `@node-rs/argon2` to `desktop` dependencies (native, auto-unpacked).
- `bindings.ts`: `activateBinding({ staffCodeOrEmail, pin })` calls
  `POST /api/pos/staff/authorize`; on success generate a 16-byte device salt, compute
  `verifier = Argon2id(pin, salt)` via IPC, store
  `{ staffUserId, staffId, name, role, bindingId, bindingToken, pinVersion, salt,
  verifier, failedAttempts: 0, lockedUntil: null }` in local-only `staff_binding`.
  `mustChangePin` routes to a forced PIN-change screen before the shift.
- `verifyPin(bindingId, pin)`: if `lockedUntil > now` reject `PIN_LOCKED`; compare via IPC;
  on failure increment attempts, lock for `pos.pinLockMinutes` after
  `pos.pinMaxAttempts`; on success reset counters, set the in-memory session (`staff`,
  `binding`, `shiftId` null) and lock on app restart (no persisted login).
- Manager unlock: choose an active MANAGER/ADMIN binding whose `lockedUntil` and failure
  counters are independent; correct manager PIN clears the cashier binding's lock and
  records a local `lockout_unlock` event (synced as an audit note on the next transaction
  or simply kept local; server audit is not required for a local unlock).
- `changePin` calls the server endpoint, then replaces the local verifier/salt/binding;
  if offline, show "connect to change PIN" but allow login with the current PIN.
- Bindings older than 90 days or with `pinVersion` mismatch are marked `needs_authorization`
  and blocked until online.
- Never store the raw PIN. The verifier and binding token live in the encrypted DB; the
  DB key is safeStorage-protected.

**Verify:** unit tests for hash/verify/lockout/unlock; E2E: activate (online) → change PIN →
quit → relaunch offline → login works; 5 wrong PINs lock; manager PIN unlocks; wrong
manager PIN does not; deactivated staff binding fails on next online validation.
**Commit:** `feat(desktop): add offline pin login and manager unlock`

## Task 5 — Shift lifecycle (local) and server application

**Files:** `desktop/src/renderer/lib/shift/shift-service.ts`,
`desktop/src/renderer/lib/shift/shift-repository.ts`,
`desktop/src/renderer/routes/shift.tsx`,
`desktop/src/renderer/components/shift/open-shift-dialog.tsx`,
`desktop/src/renderer/components/shift/cash-movement-dialog.tsx`,
`desktop/src/renderer/components/shift/close-shift-dialog.tsx`,
`api/src/modules/pos/pos.service.ts`, `api/src/modules/pos/pos.repository.ts`,
`api/src/modules/pos/pos.types.ts`, `api/src/modules/pos/pos.test.ts`

- Local `shift-service.openShift({ openingFloatMinor })`: require a logged-in cashier and
  no open shift for this terminal; allocate
  `number = ${terminal.code}-S-${yyyyMMdd}-${NN}` from `document_sequence` (scope
  `shift`, day `Africa/Accra`); insert `shift` (status OPEN) + `outbox` row
  `SHIFT_OPEN` in one `db.writeTransaction`; return the shift.
- `recordCashMovement({ type, amountMinor, reason })`: require an open shift, insert
  `cash_movement` + outbox `CASH_MOVEMENT` atomically.
- `closeShift({ countedCashMinor, note })`: compute
  `expected = openingFloat + Σ cash tenders − Σ change + Σ cash_in − Σ cash_out` from
  local sales/movements; `variance = counted − expected`; update `shift` (status CLOSED,
  counted/expected/variance) + outbox `SHIFT_CLOSE` atomically. Selling is blocked while
  no shift is open if `pos.salesRequireOpenShift`. Closing while the outbox has pending
  sales is allowed; the close row is ordered after them.
- Server `pos.service` (called by the Plan 05 upload dispatcher; unit-tested directly
  here):
  - `openShift(device, payload)`: lock/validate terminal; reject if an OPEN shift exists
    with a different id; insert the shift (client id) and audit `pos.shift.opened`.
  - `recordCashMovement(device, payload)`: shift must be OPEN, branch/terminal/device must
    match; insert and audit `pos.cash.movement`.
  - `closeShift(device, payload)`: shift must be OPEN; recompute
    `serverExpected = openingFloat + Σ cash tenders − change + Σ cash in/out` from applied
    sales/movements; store `clientExpectedCashMinor`, `serverExpectedCashMinor`,
    `varianceMinor = counted − serverExpected`; if
    `|clientExpected − serverExpected| > 0` create `SHIFT_VARIANCE_MISMATCH`; audit
    `pos.shift.closed`.
  - All functions accept `occurredAt` and run inside the caller's transaction; idempotency
    is owned by the Plan 05 dispatcher.
- POS shift screen: big touch UI, opening float keypad, cash in/out list, running expected
  cash, close with counted cash and variance (green/red), shift number, cashier, opened
  time. Header shows the shift state. The route is reachable after PIN login and blocks
  `/sell` until open.

**Verify:** API unit tests for one-open-per-terminal, wrong device, close arithmetic,
variance conflict; desktop unit tests for local expected/variance and atomic writes;
E2E open → cash in → close offline → row persists after restart.
**Commit:** `feat(pos): add offline shift lifecycle and server application`
